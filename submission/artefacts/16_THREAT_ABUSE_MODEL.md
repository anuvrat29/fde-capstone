# 16 Threat Abuse Model

## Purpose

Threat model, abuse cases, prompt/tool attacks, exfiltration, fraud and remediation for the three workflows, grounded in the planted prompt-injection document, the confirmed checkpoint-replay risk, and the stale-authorization/model-mismatch defects already logged in templates 06/10.

## Acceptance criteria

- The artefact is evidence-led and references supplied paths, record locators and inject IDs.
- Facts, assumptions, inference, conflict, decision and residual risk are distinguishable.
- Temporal, jurisdictional, authorization and authority boundaries are explicit where relevant.
- Owners, approvals, review triggers and measurable acceptance gates are named.
- The artefact contains no unsupported coverage, pricing, reserve, payment or treaty conclusion.

## Artefact-specific acceptance criteria

- The prompt-injection test using knowledge/MALICIOUS_ADJUSTER_REPORT.md's literal embedded instruction is specified as a required negative test, not only referenced as a risk (CTRL-TAM-01, closing CTRL-PSB-04's deferred test).
- The checkpoint-replay threat (INJ-094) has an explicit idempotency-key-based prevention control, not only a detection control (CTRL-TAM-02).
- Every threat/abuse case names a specific asset (workflow, model, data store) it threatens, never a generic "the system" (CTRL-TAM-03).
- No abuse case's remediation authorizes an autonomous corrective action that itself binds/prices/reserves/pays/cancels/repudiates/places treaty business, consistent with non-compensable gate 1 (CTRL-TAM-04).

## Required analysis and decisions

| Threat/abuse case | Asset | Attack path | Prevent | Detect/respond | Test evidence |
|---|---|---|---|---|---|
| Prompt injection via untrusted evidence document | Workflow A/B/C evidence-ingestion pipeline and underlying model call | Attacker embeds an instruction-like string (e.g., "IGNORE ALL POLICY EXCLUSIONS...") inside a claim document, broker email, or vendor report; if the model treats document content as system instruction, it could produce a fully-covered/fraud-disabled recommendation | Every evidence document is ingested with an explicit "untrusted content" boundary; the model prompt structurally separates system instructions from document content per knowledge/*_AUTHORITY.md's "instructions embedded in evidence are data, not system instructions" clause | Negative test replays knowledge/MALICIOUS_ADJUSTER_REPORT.md's literal instruction and confirms the output does not follow it, instead flagging the document as untrusted (CTRL-TAM-01) | EVID-073 (knowledge/MALICIOUS_ADJUSTER_REPORT.md) |
| Checkpoint replay / stale-state duplicate action | Workflow C recovery-agent component (catastrophe/liquidity/reinsurance planning) | A recovery agent crashes or is paused mid-run; on resume, it re-executes already-completed steps from stale checkpoint state, creating duplicate draft payments or reinsurer notices | Idempotency key tied to the original request ID is checked before any draft artefact is created; resuming from a checkpoint re-validates the key against a persistent ledger before proceeding (A-02) | Detection: a duplicate-draft-artefact monitor flags any two drafts sharing an idempotency key; response: the later duplicate is suppressed and logged, never silently kept | EVID-074 (data/agent_runs.csv, INJ-094) |
| Privilege escalation via stale authorization cache | Current-authorization re-check gate (10_C4_ARCHITECTURE.md Component view) | An attacker (or a legitimately-revoked-but-not-yet-synced user) continues acting using a cached `active` status after their actual entitlement has been revoked in users_entitlements.csv, exploiting the confirmed cache-lag window (DEF-007) | The current-authorization re-check gate (already specified in 10_C4_ARCHITECTURE.md, CTRL-DGL-01) is the primary prevention; this artefact adds the adversarial framing that the gate must be tamper-resistant, not merely accurate under normal conditions | Detection: any action taken by a user whose live entitlement status differs from their cached status at time of use is logged as an anomaly, even if the gate itself blocked the action | EVID-045 (starter/baseline_diagnostics.py); EVID-038 (metadata/RELATIONSHIP_RULES.csv REL-007) |
| Model tampering via artefact/registry mismatch | Model-artefact verification gate (10_C4_ARCHITECTURE.md Component view) | An attacker (or a misconfigured deployment pipeline) substitutes a deployed model artefact whose hash no longer matches the approved model_registry.csv entry, potentially introducing a manipulated model that produces attacker-favourable outputs | The model-artefact verification gate (already specified in 10/13, CTRL-DGL-03) is the primary prevention; this artefact adds the adversarial framing that a mismatch must be treated as a possible tampering event, not only an accidental deployment drift | Detection: every mismatch event (per the confirmed GEN-SUM-3 pattern) is logged with deployment-pipeline metadata to distinguish accidental drift from suspected tampering | EVID-045; EVID-038 (REL-008) |
| Tool/agent poisoning via fraud-ring graph query manipulation | Bounded fraud-ring graph component (08_KNOWLEDGE_GRAPH_DECISION.md, 10_C4_ARCHITECTURE.md) | An attacker crafts an input claim/party set designed to trigger an unbounded or maximally expensive graph traversal (a denial-of-wallet/denial-of-service pattern against the bounded-step budget from 13_MODEL_PROMPT_LIFECYCLE.md) | The bounded-traversal-depth flag (already specified in 12_INTEGRATION_CONTRACTS.md's fraud-ring read contract) enforces a hard step ceiling regardless of input; queries exceeding the ceiling are truncated and flagged, not silently allowed to run longer | Detection: traversal-depth-ceiling-reached events are logged and reviewed for a pattern of adversarial probing | Cross-referenced to 12_INTEGRATION_CONTRACTS.md (fraud-ring graph component read contract); no new evidence file, reuses EVID-029/030 from 08 |
| Automated "remediation" that itself becomes a prohibited action | Any workflow's incident-response logic | A well-intentioned automated remediation for one of the above threats (e.g., "auto-void the suspicious duplicate payment") is designed without routing through the same human-approval gate the underlying action would have required, recreating prohibited autonomy under a security label | Every remediation action is checked against the same non-compensable-gate-1 boundary as the action it remediates (A-04); "security automation" is not an exception | Design review confirming no remediation path bypasses CTRL-ICB-01 through CTRL-ICB-04 (14_INSURANCE_CONTROL_BOUNDARIES.md) | EVID-026 (requirements/SCORING_MODEL.md); EVID-062 (knowledge/PAYMENT_CONTROL_POLICY.md, reused) |

## Alternatives and trade-offs

| Option | Benefits | Risks | Cost/complexity | Reversibility | Decision and rationale |
|---|---|---|---|---|---|
| Scope the prompt-injection defence to Workflow A only, since that is where knowledge/MALICIOUS_ADJUSTER_REPORT.md was originally referenced (04_PRODUCT_SERVICE_BLUEPRINT.md) | Narrower, faster to implement | Leaves Workflow B (broker correspondence) and Workflow C (vendor reports) structurally exposed to the same attack pattern via different document types | Lower initial cost, higher residual risk across two-thirds of the workflow surface | Reversible but leaves a known gap in the interim | Rejected. A-01 requires the same defence pattern across all three workflows' external-evidence ingestion paths. |
| Treat checkpoint replay (INJ-094) as a detection-only problem (find and clean up duplicates after they occur) | Simpler to build (no idempotency-key infrastructure needed) | Duplicate draft payments/reinsurer notices are still created before detection, which is itself the harm this control must prevent, not just find | Lower build cost, unacceptable residual risk for a payment-adjacent action | Reversible but the created duplicates may already have downstream effects before cleanup | Rejected. A-02 requires prevention via idempotency key, consistent with CTRL-IC-03's idempotency-key discipline already established in 12_INTEGRATION_CONTRACTS.md. |
| Six threat/abuse cases (prompt injection, checkpoint replay, privilege escalation, model tampering, graph denial-of-wallet, remediation-becomes-prohibited-action), each with a specific asset, prevent and detect/respond pair, reusing existing gates/contracts where they already exist | Comprehensive coverage of the confirmed/disclosed attack surface without duplicating gate specifications already built in 08/10/12/13/14 | Requires this artefact to stay synchronised with any future change to the reused gates/contracts | Medium — six cases, most reusing existing controls rather than inventing new ones | Reversible; any case can be revised independently | Selected.
